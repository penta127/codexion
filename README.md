# Codexion

> 締切に支配される前に、リソースを奪い取れ

**バージョン: 1.5**

## 概要

限られた USB ドングルを複数のコーダーが取り合う、スリリングな並行処理課題です。POSIX スレッド、mutex、適切なスケジューリングを使い、共有リソースの同期を管理してください。燃え尽き（burnout）が発生する前に、リソース競合を制御することが目標です。

## はじめに

プログラミング（一般に「コーディング」とも呼ばれる）は、特定の計算課題を達成する実行可能なソフトウェアを設計・構築する作業です。そこには、分析、アルゴリズムの作成、精度とリソース消費の評価、選択したプログラミング言語での実装が含まれます。初期のコンピュータは、ハードウェアが理解するバイナリ命令列である機械語で直接プログラムされていました。その後、より高水準の言語が開発され、コーダーはより抽象的に考えを表現できるようになりました。

コーディング文化は純粋に技術的な側面だけにとどまりません。オープンソースのコミュニティ、コワーキングスペース、ハッカソンなどの共有環境で、問題解決・創造性・協働を結びつけます。このような場所では、コーダーはコードを書くだけでなく、デバッグ、リファクタリング、ツールの共有も行います。コーヒーのように豊富なリソースもあれば、専用ハードウェアドングルやライセンスされた開発環境のように、ボトルネックを避けるため慎重に共有しなければならない限られたリソースもあります。

かつて哲学者が真理や存在を議論したように、現代のコーダーはプログラミングパラダイム、デザインパターン、倫理的なソフトウェア開発について議論します。速度と保守性のどちらを優先すべきか。今リファクタリングすべきか、製品が価値を証明してからにすべきか。進行を止めずに、チームが共有リソースへ公平にアクセスするにはどうすればよいか。

歴史的にプログラミングは個人作業であることが多かった一方、バージョン管理システム、リアルタイムエディタ、分散型の課題管理ツールの発展により、ますます社会的・協調的な活動になりました。それと同時に、並行性と同期は重要な技能になりました。複数の開発者やプロセスが互いに干渉せず動作するようにすることは、コードを書くことと同じくらい重要です。

タイムゾーンをまたいでチームが働き、時間制限付きまたは希少なハードウェアを利用する現代では、正しいコードを書くだけでは不十分です。リソースを公平かつ効率的に共有するプロトコルを設計する必要があります。このシミュレーションでは、共有スペースで量子コードをコンパイルするために 2 本の希少な USB ドングルを必要とするコーダーを扱います。彼らは協調し、デッドロックを避け、燃え尽きを防がなければなりません。協働的なコーディングの世界では、人生と同じく、アクセスとタイミングがすべてです。

## AI に関する指針

### 背景

学習の過程で、AI はさまざまな作業を支援できます。AI ツールの能力と、作業にどう役立つかを十分に探求してください。ただし、常に注意深く使い、結果を批判的に評価してください。コード、ドキュメント、アイデア、技術的説明のいずれであっても、質問が適切に構成されていることや、生成内容が正確であることを完全には保証できません。間違いや盲点を避けるために、仲間は貴重な助けになります。

### 主なメッセージ

- AI を使い、反復的または退屈な作業を減らす。
- コーディング・非コーディングの両方で、将来のキャリアに役立つプロンプト作成スキルを身につける。
- AI システムの仕組みを学び、よくあるリスク、バイアス、倫理上の問題を予測・回避する。
- 仲間と協力しながら、技術スキルとパワースキルの両方を伸ばし続ける。
- 自分が完全に理解し、責任を負える AI 生成コンテンツだけを利用する。

### 学習者向けルール

- AI ツールを倫理的に使い、潜在的なバイアスを減らせるよう、時間をかけてその仕組みを理解する。
- プロンプトを入力する前に問題を考える。そうすることで、正確な語彙を使った、より明確・詳細・適切なプロンプトを書ける。
- AI が生成したものは、体系的に確認、レビュー、検証、テストする習慣をつける。
- 自分だけの検証に頼らず、常に仲間によるレビューを求める。

### このフェーズで得られること

- 汎用的・分野特化型の両方のプロンプトスキルを伸ばす。
- AI ツールを効果的に使い、生産性を上げる。
- 計算論的思考、問題解決、適応力、協働力をさらに強化する。

### 補足と例

- 試験や評価など、真の理解を示す必要がある場面に繰り返し直面します。技術スキルと対人スキルの両方を継続して磨いてください。
- 自分の考えを説明し仲間と議論すると、理解の穴が見つかることがよくあります。仲間との学びを優先してください。
- AI はあなた固有の文脈を持たないため、一般的な回答をしがちです。同じ環境を共有する仲間は、より関連性が高く正確な洞察を与えられます。
- AI は最もありそうな回答を生成しがちですが、仲間は別の観点や重要なニュアンスを提供できます。品質確認の役割として仲間を頼ってください。

**良い実践例**: AI に「ソート関数はどうテストすればよいですか？」と尋ね、いくつかの案を試し、結果を仲間と確認する。一緒にアプローチを改善する。

**悪い実践例**: AI に関数全体を書かせて、プロジェクトにコピー＆ペーストする。ピア評価で動作や理由を説明できず、信用を失い、課題に失敗する。

**良い実践例**: AI を使ってパーサの設計を補助し、その後で仲間とロジックを追う。2 個のバグを見つけ、一緒に書き直して、より良く・よりきれいで・完全に理解した実装にする。

**悪い実践例**: プロジェクトの重要な部分を Copilot に生成させる。コンパイルは通るが、パイプをどう処理しているか説明できない。評価で正当化できず、課題に失敗する。

## 共通指示

- プロジェクトは C 言語で作成すること。
- プロジェクトは Norm に従うこと。ボーナス用のファイルや関数も Norm チェックの対象であり、Norm エラーがあれば 0 点となります。
- 未定義動作を除き、関数が予期せず終了してはなりません（segmentation fault、bus error、double free など）。発生した場合、プロジェクトは機能しないものと見なされ、評価では 0 点となります。
- ヒープに確保したメモリは、必要なときにすべて適切に解放すること。メモリリークは認められません。
- 課題で必要とされる場合、`cc` と `-Wall -Wextra -Werror` を使って必要な成果物へソースをコンパイルする Makefile を提出すること。不要な再リンクをしてはなりません。
- Makefile には少なくとも `$(NAME)`、`all`、`clean`、`fclean`、`re` のルールを含めること。
- ボーナスを提出する場合、メインパートでは許可されないヘッダ、ライブラリ、関数を追加する `bonus` ルールを Makefile に含めること。課題で別途指定がない限り、ボーナスは `_bonus.{c/h}` ファイルに置くこと。必須パートとボーナスは別々に評価されます。
- `libft` の使用が許可されている場合は、ソースと関連する Makefile を `libft` フォルダへコピーすること。プロジェクトの Makefile は、その Makefile を使ってライブラリをコンパイルしてからプロジェクトをコンパイルすること。
- 提出・採点対象ではありませんが、テストプログラムを作ることを推奨します。自分と仲間の作業を容易にテストでき、防衛（defence）時にも役立ちます。防衛時には、自分のテストおよび／または評価する仲間のテストを自由に使えます。
- 指定された Git リポジトリに作業を提出すること。採点されるのは Git リポジトリ内の作業だけです。Deepthought が採点する場合は、ピア評価の後に行われます。Deepthought の採点中に作業のいずれかの箇所でエラーが起きると、評価は停止します。

## 課題の概要

この課題で成功するために知っておくべきことは次のとおりです。

- 1 人以上のコーダーが、円形の包括的なコワーキングハブに座っています。中央には共有の **Quantum Compiler** があります。
- コーダーは **コンパイル**、**デバッグ**、**リファクタリング**を交互に行います。コンパイル中はデバッグもリファクタリングもせず、デバッグ中はコンパイルもリファクタリングもせず、リファクタリング中も同様です。
- テーブル上には USB ドングルがあります。ドングルの数はコーダーの数と同じです。
- 量子コードのコンパイルには、両手に 1 本ずつ、同時に接続した 2 本のドングルが必要です。コーダーは左と右のドングルを取ってコンパイルします。
- コンパイルを終えると、コーダーは両方のドングルをテーブルに戻してデバッグを始めます。デバッグの後はリファクタリングを始めます。コンパイル不足により誰かが燃え尽きると、シミュレーションは終了します。
- 各コーダーは定期的にコンパイルする必要があり、決して燃え尽きてはなりません。
- コーダー同士は通信しません。
- コーダーは、他のコーダーが燃え尽きようとしているかを知りません。
- 言うまでもなく、コーダーは燃え尽きを避けるべきです。

## 全体ルール

次のルールに従う **1 つのプログラム**を書いてください。

- グローバル変数は禁止です。
- プログラムは次の必須引数を受け取ります。

```text
number_of_coders time_to_burnout time_to_compile time_to_debug
time_to_refactor number_of_compiles_required dongle_cooldown scheduler
```

| 引数 | 説明 |
| --- | --- |
| `number_of_coders` | コーダーの人数であり、ドングルの数でもあります。 |
| `time_to_burnout` | ミリ秒単位。最後にコンパイルを開始してから、またはシミュレーション開始から、この時間内にコンパイルを開始しなければコーダーは燃え尽きます。 |
| `time_to_compile` | ミリ秒単位。コンパイルにかかる時間です。この間、2 本のドングルを保持していなければなりません。 |
| `time_to_debug` | ミリ秒単位。デバッグに費やす時間です。 |
| `time_to_refactor` | ミリ秒単位。リファクタリングに費やす時間です。完了後、コーダーはすぐにドングルを取得して再びコンパイルしようとします。 |
| `number_of_compiles_required` | 全コーダーが少なくともこの回数だけコンパイルするとシミュレーションは終了します。それ以外では、誰かが燃え尽きた時点で終了します。 |
| `dongle_cooldown` | ミリ秒単位。ドングルは解放されてから、このクールダウン時間が経過するまで利用できません。 |
| `scheduler` | 複数のコーダーが要求したとき、どのコーダーにドングルを渡すか決める調停方針です。`fifo` または `edf` のいずれかでなければなりません。 |

- `fifo` は **First In, First Out** を意味します。最初に到着した要求を持つコーダーにドングルを渡します。
- `edf` は **Earliest Deadline First** を意味します。`last_compile_start + time_to_burnout` で計算される締切が最も早いコーダーにドングルを渡します。
- 各コーダーには、`1` から `number_of_coders` までの番号が付きます。
- コーダー番号 `1` はコーダー番号 `number_of_coders` の隣に座ります。それ以外のコーダー番号 `N` は `N - 1` と `N + 1` の間に座ります。
- すべての引数は必須です。負の数、整数以外、`fifo`・`edf` 以外のスケジューラなど、不正な入力は拒否してください。

### ログについて

コーダーの状態変化は、すべて次の形式で出力してください。

```text
timestamp_in_ms X has taken a dongle
timestamp_in_ms X is compiling
timestamp_in_ms X is debugging
timestamp_in_ms X is refactoring
timestamp_in_ms X burned out
```

`timestamp_in_ms` は現在のタイムスタンプ（ミリ秒）に、`X` はコーダー番号に置き換えます。

- 表示される状態メッセージ同士が混ざってはなりません。
- コーダーが燃え尽きたことを知らせるメッセージは、実際の燃え尽きから **10 ms 以内**に表示すること。
- コーダーの燃え尽きは避けてください。

期待されるログ形式の例:

```text
0 1 has taken a dongle
1 1 has taken a dongle
1 1 is compiling
201 1 is debugging
401 1 is refactoring
402 2 has taken a dongle
403 2 has taken a dongle
403 2 is compiling
603 2 is debugging
803 2 is refactoring
1204 3 burned out
```

**精度要件:** 燃え尽きログは、実際の燃え尽き時刻から 10 ms 以内に表示する必要があります。ハードウェアや OS のスケジューリングは計測時刻にわずかな影響を与えるため、テスト時には最小限の許容差を認めてください。

**時間に関する考慮:** パフォーマンス計測へのハードウェアの影響を減らすため、可能であれば実時間クロックではなく CPU 使用時間を使うことを検討してください。ただし、このプロジェクトでは単純さのため、`gettimeofday()` を使う実時間計測が許可され、推奨されています。

## 必須パート

| 項目 | 内容 |
| --- | --- |
| プログラム名 | `codexion` |
| 提出ファイル | ルートの Makefile と、任意のフォルダ内の `*.c`・`*.h` |
| Makefile | `NAME`、`all`、`clean`、`fclean`、`re` |
| 引数 | `number_of_coders time_to_burnout time_to_compile time_to_debug time_to_refactor number_of_compiles_required dongle_cooldown scheduler` |
| 許可される外部関数 | `pthread_create`、`pthread_join`、`pthread_mutex_init`、`pthread_mutex_lock`、`pthread_mutex_unlock`、`pthread_mutex_destroy`、`pthread_cond_init`、`pthread_cond_wait`、`pthread_cond_timedwait`、`pthread_cond_signal`、`pthread_cond_broadcast`、`pthread_cond_destroy`、`gettimeofday`、`clock_gettime`、`usleep`、`write`、`malloc`、`free`、`printf`、`fprintf`、`strcmp`、`strlen`、`atoi`、`memset` |
| Libft | 使用不可 |
| 内容 | スレッドと mutex を用いるコーダー（C） |

必須パートの固有ルールは次のとおりです。

- 各コーダーは `pthread_create` を使う 1 つのスレッドで表現すること。
- 各コーダーの組の間には 1 本のドングルがあります。したがって複数のコーダーがいる場合、各コーダーには左側と右側に 1 本ずつドングルがあります。コーダーが 1 人だけの場合、テーブル上にはドングルが 1 本だけです。
- コーダーがドングルを複製することを防ぐため、各ドングルの状態を `pthread_mutex_t` で保護すること。待機キューを管理するために `pthread_cond_t` を使ってよいです。
- ドングルのクールダウンは必須です。コーダーがドングルを解放した後、`dongle_cooldown` ミリ秒が経過するまで、そのドングルは再取得できません。
- 公平な調停は必須です。複数のコーダーが同じドングルを要求する場合、ドングルは `scheduler` に従ってアクセスを許可しなければなりません。`fifo` では要求の到着順に処理します。`edf` では、燃え尽き締切（`last_compile_start + time_to_burnout`）が最も早いコーダーを優先します。

  > タイムスタンプの精度のため、実際には同一の締切が発生することはまれです。同点の場合にも完全に決定的な EDF 方針となるよう、タイブレークルールが必要です。

- パラメータが実現可能である限り、`edf` スケジューリング下で、どのコーダーもドングルを得られず飢餓状態になったり燃え尽きたりしないことを保証すること。
- 個別の **monitor スレッド**が燃え尽きを正確に検出し、シミュレーションを停止すること。燃え尽きログは実際の燃え尽きから 10 ms 以内に出力すること。
- ログ出力は直列化し、2 つのメッセージが 1 行に混ざらないようにすること（出力を保護する mutex を使用）。
- シミュレーションは、コーダーが燃え尽きたとき、または全コーダーが `number_of_compiles_required` 回コンパイルしたときに終了します。
- コードは `-Wall -Wextra -Werror -pthread` でコンパイルできること。
- FIFO / EDF スケジューリングのために、優先度キュー（ヒープ）を実装すること。標準ライブラリの優先度キューは使用できません。
- すべてのメモリを適切に確保・解放し、メモリリークがないこと。

シミュレーション実行例:

```text
0 1 has taken a dongle
2 1 has taken a dongle
2 1 is compiling
202 1 is debugging
402 1 is refactoring
405 2 has taken a dongle
406 2 has taken a dongle
406 2 is compiling
606 2 is debugging
806 2 is refactoring
900 3 has taken a dongle
902 3 has taken a dongle
902 3 is compiling
1102 3 is debugging
1302 3 is refactoring
1505 4 burned out
```

この例は、複数コーダーの動作順を示しています。各 `is compiling` の前には必ず 2 行の `has taken a dongle` があり、`burned out` はコーダーが締切を過ぎた時点で表示されます。

## README の要件（原文）

Git リポジトリのルートに `README.md` を用意する必要があります。このファイルの目的は、プロジェクトを知らない人（仲間、スタッフ、採用担当者など）が、プロジェクトの内容、実行方法、関連情報の場所を素早く理解できるようにすることです。

提出用の `README.md` には少なくとも以下を含める必要があります。

- 最初の行はイタリック体とし、次の文にすること: `This project has been created as part of the 42 curriculum by <login1>[, <login2>[, <login3>[...]]].`
- プロジェクトの目的と簡単な概要を明確に示す「Description」セクション。
- コンパイル、インストール、実行に関する情報を含む「Instructions」セクション。
- トピックに関する古典的な参照資料（ドキュメント、記事、チュートリアルなど）と、AI をどの作業・どの部分で使用したかを説明する「Resources」セクション。

プロジェクトによっては、使用例、機能一覧、技術的選択など、追加セクションが必要になる場合があります。必要な追加内容は明示されます。

このプロジェクトでは、さらに以下を含める必要があります。

- 「Blocking cases handled」セクション: デッドロック防止と Coffman の条件、飢餓防止、クールダウン処理、正確な燃え尽き検出、ログの直列化など、解決したすべての並行処理問題を説明すること。
- 「Thread synchronization mechanisms」セクション: 実装で使用したスレッドプリミティブ（`pthread_mutex_t`、`pthread_cond_t`、独自イベント実装）と、それらが共有リソース（ドングル、ログ、monitor の状態）へのアクセスをどう協調させるかを説明すること。競合状態をどう防ぐか、コーダーと monitor 間でスレッドセーフな通信をどう実現するかの例も含めること。

> 提出用 README は英語で書く必要があります。

## 提出とピア評価

通常どおり、課題を Git リポジトリに提出してください。防衛時に評価されるのは、リポジトリ内の作業だけです。ファイル名が正しいことを再確認してください。

### Recode（再コーディング）に関する指示

評価中に、プロジェクトへの簡単な変更を求められることがあります。これは、軽微な振る舞いの変更、数行のコードの追加・書き換え、簡単に追加できる機能などです。

この手順はすべてのプロジェクトに適用されるわけではありませんが、評価ガイドラインに記載されている場合は準備しておく必要があります。この手順は、プロジェクトの特定部分を実際に理解しているかを確認するためのものです。

変更は、普段の開発環境など任意の環境で行えます。特別な制限時間が定められていない限り、数分で完了できる内容である必要があります。たとえば、関数やスクリプトへの小さな更新、表示の変更、追加情報を保存するデータ構造の調整などを求められる場合があります。

詳細（範囲、対象など）は評価ガイドラインに示され、同じプロジェクトでも評価ごとに異なることがあります。
